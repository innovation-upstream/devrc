# `scripts/`

Operational scripts for the devrc environment. **435 tracked files**: 50 top-level entrypoints (plus
this README) and 13 subsystem directories that are small applications in their own right.

This index covers the 50 top-level entrypoints individually and the subsystems one line each. It
deliberately does not enumerate every file — most of the tree is `test_*.py`, and a flat listing
would be noise that goes stale on the next commit.

Descriptions come from each script's own header comment. Most are self-documenting: run with
`--help` where supported, or read the header.

There is no `--skip-agent-worktrees` — it was the opt-in spelling and is gone rather than left as a no-op alias. `--exclude-path GLOB` (repeatable) adds operator-typed row filters. An excluded row is still scanned, classified and printed (as `dead (excluded)`, with its own summary line and column), is **never** removed, and is **not** counted toward `--confirm N` — and the report states, right under the removable count, how many further `dead` rows were spared, so the number can never be read as "everything was covered". 🔴 **A `dead` worktree carrying SUBMODULES is never `removable`** (#931): `git worktree remove` refuses on one outright (`rc=128 fatal: working trees containing submodules cannot be moved or removed`), and because the tool never passes `--force` those rows are **permanently** unremovable — not transiently, and re-running never converges. Before this, `removable` counted them and `--confirm N` was derived from that count, so the first real fleet `--execute` offered **107** where **53** was achievable (`removed=53 skipped=0 failed=54`, every failure that one string) — a ~2× overcount in the operator's primary safety number. They now stay `dead`, stay printed and drop out of `removable`, with a summary line under the removable count and a `--verbose` evidence line naming the submodule. 🔴 **The predicate is NOT "does `.gitmodules` exist"** — MEASURED against git 2.55.0 on the hermetic fixtures enumerated in `worktree_submodules`' docstring (count them there; a total restated here drifts, and this row said "five" while the docstring listed six): a tracked `.gitmodules` whose submodule is **uninitialised** REMOVES FINE (so keying on it over-blocks); a **deinitialised** submodule leaves no populated gitlink and is still REFUSED (so keying on populated gitlinks under-blocks); an **old-style embedded `.git` directory** creates no `modules/` store and is REFUSED (so keying on `modules/` alone under-blocks); and an **EMPTY `modules/` store** is REFUSED too — git's own source calls that a knowingly-accepted false positive, so the tool mirrors it rather than being cleverer, because being cleverer here returns `failed=1`. It is the OR of git's own two arms, checked in git's order: *this worktree's* git dir has a `modules/` store (`rev-parse --git-path modules`, which resolves per-worktree), **or** a gitlink in the index is populated. An **unknowable** answer blocks rather than permits, and the check runs a second time in the executor immediately before the destructive step, so a submodule initialised by a concurrent session between scan and removal produces a `SKIP`, never a `failed=`. 🔴 **The index arm reads `ls-files -s -z` as BYTES.** Without `-z`, `core.quotePath` renders a submodule at `vendôr` as the literal `"vend\303\264r"`, the stat misses and the arm answers `False` over a worktree git refuses on — `failed=` straight back. But `-z` also makes git emit paths RAW, and strict utf-8 decoding then aborts the ENTIRE scan (`UnicodeDecodeError`, bare traceback, zero classified rows) on **any** undecodable tracked filename in **any** worktree — measured with a single `caf\xe9.txt` in a repo with no submodules at all. ⚠ **"Tracked" is that measurement's scope, not the hazard's**: `ls-files` and `diff` only see tracked content, but `worktree_dirty` reads `status --porcelain=v1 --untracked-files=normal`, so for THAT call one **untracked** file is enough — measured at #975's HEAD, a worktree with `core.quotePath=false` and a single untracked `caf\xe9.txt` aborts the whole scan. `list_worktrees` no longer does — #944 moved it, `rev-parse --git-path` and `worktree remove`'s stderr onto `_git_raw` — but `worktree_dirty` still reads through `_git`, so **the abort class is NOT closed**. So this one call goes through `_git_raw` and decodes twice on purpose: `os.fsdecode` (surrogateescape) to REACH the path, `_printable` (U+FFFD) to SHOW it, since a lone surrogate raises `UnicodeEncodeError` at `print()` and would merely move the abort. 🔴 **That was ONE call, not the class** (#944): a worktree whose **DIRECTORY NAME** holds an undecodable byte took the whole scan down too — measured identically on `origin/main` and on #935's branch, so pre-existing, not a regression. Three more sites, and only the first is the obvious one: **`worktree list --porcelain`** emits the path raw and unquoted (`core.quotePath` does **not** apply to it — measured byte-identical with the setting on and off, so unlike the `-z` case there was never any quoting keeping it ASCII); **`rev-parse --git-path modules`** *answers* with a path the tool never supplied (`<repo>/.git/worktrees/<DIRECTORY NAME>/modules`), so fixing only the porcelain arm **moved** the abort here rather than removing it, under default git config, with no submodule in the fixture; and **`worktree remove`'s stderr**, where git names the path back at us, so the arm whose only job is to report a removal that did *not* happen was itself the abort. All three now read bytes. 🔴 **The worst of them is `execute_removals`**, which re-runs the first two per row and reads the third: an abort there fires *after* some removals and *before* the `execute: removed= skipped= failed=` line, leaving no record of what was deleted. 🔴 **Every row therefore carries each of its paths TWICE** and they are not interchangeable: `path` / `repo` (`_printable`, U+FFFD) are what the report prints, sorts on, glob-matches and serialises, and are never used to *reach* anything; **`path_fs` and `repo_fs` (`os.fsdecode`, surrogateescape) are NEW `--out` row fields** and are what reach the filesystem, git's argv and the executor's identity comparison, and are never printed. `path` is the reported one because the failure modes are asymmetric — a display site that forgets to convert *crashes*, a filesystem site that forgets degrades to `cannot-tell`. ⚠ **"Never touches I/O" is what this row and the tool's own docstrings used to say, and it is false**: `scan_repo` hands the printable path to `path_excluded`, which resolves symlinks (`_path_candidates` → `_resolve_or_none` → `Path.resolve()`, i.e. `readlink`/`lstat`) so a filter matches either spelling of a symlinked tree. Deliberate and benign — resolution is best-effort and a miss costs one candidate form, never a removal — but it *is* I/O, and the absolute wording had two comments in one file disagreeing. 🔴 **`repo` was the site the first #944 round MISSED, and skipping it did not leave the abort where it was — it MOVED it.** `row["repo"]` never came from git at all (it is `discover_repos`/argv, already `os.fsdecode`d) and went into the row raw, while `render_text`'s per-repo table printed it: a **repo** whose own directory name held an undecodable byte therefore raised `UnicodeEncodeError` at the tool's single `print(render_text(…))` — and because the whole report is built before a byte of it is written, **every other repo's rows died with it: zero rows, rc 1, bare traceback**, under *default* git config in the *default* output format (`--format json` survived only because `json.dumps` defaults to `ensure_ascii=True` and escapes a lone surrogate instead of raising). Measured on a two-repo `--scan-root`, one ASCII and one undecodable: `origin/main` → `UnicodeDecodeError` in `list_worktrees`; the first fix's HEAD → `UnicodeEncodeError` at `worktree-prune:2064`. It also means the headline claim "an undecodable worktree *directory name* no longer aborts" was not fully true, because the **main worktree of such a repo is exactly such a worktree**. The row fields that split are now enumerated in `ROW_PATH_FIELDS` and `row_fs` is the single place that chooses a spelling, with a seam guard asserting the *relationship* (every non-`_fs` value on every row survives `encode("utf-8")`; the `_fs` key set equals the ledger) rather than either component. ⚠ **`path_fs` and `repo_fs` do not survive `jq`.** The `--out` JSON encodes them with the unpaired escape `\udce9`, so `jq -r .path_fs` emits U+FFFD — byte-identical to the lossy `path`, i.e. `jq` gives you no more than the printable field already did. Only a surrogateescape-aware reader recovers the bytes: in Python, `json.load(...)["path_fs"].encode("utf-8", "surrogateescape")`. 🔴 **Still open, measured, NOT fixed — and it is now ONE arm, not two.** Under `core.quotePath=false`, `git status --porcelain=v1` (`worktree_dirty`) emits raw path bytes and **aborts** the whole scan — loud, loses the run — and its reach is wider than "tracked", because it reads `--untracked-files=normal` and one never-`git add`ed file is enough. The `git diff --name-only` arm that used to sit beside it here was the WORSE of the two: under the DEFAULT `core.quotePath=true` it did not abort at all, it returned the quoted literal `"caf\303\251.md"`, which fed straight back as a pathspec matched nothing, so git exited 0 with empty output, `_paths_differ` read that as `False`, `content-identical` fired, and a branch whose work never landed was reported `dead` with `removable=True` on a stock host with no flag set. That was **devrc#975**; it is FIXED and merged (#1002), verified post-merge against a pre-merge negative control that reproduces the wrong `dead`. `worktree_dirty` is what remains. 🔴 **`--repos-from` now reads with `errors="surrogateescape"`**, not strict: a repo list naming an undecodable directory used to raise `UnicodeDecodeError` before a single row was classified, and surrogateescape is also the *right* decoding rather than merely a survivable one — it is what `os.fsdecode` gives argv, so `--repos-from` and `--repo` hand `collect_repos` the same string for the same directory. 🔴 **`parse_worktree_porcelain` taking `bytes` also fixed a record-splitting bug nobody had reported**: `str.splitlines()` splits on `\v`, `\f`, `\x1c`-`\x1e`, U+0085 and U+2028/9 as well as newlines, none of which git treats as a record separator, so a worktree path containing one was torn into two bogus records; `bytes.splitlines()` splits only on `\n` / `\r` / `\r\n`. Strictly better — do not "restore" the `str` form. 🔴 **The `content-identical` arm reads its changed-path set the same way, and for a worse reason (#975).** Both halves — `landing_signals`' `diff --name-only -z` listing and `_paths_differ`'s `diff --name-only -z` comparison — go through `_git_raw` as BYTES. Only the LISTING decodes (`os.fsdecode`, surrogateescape, so the str re-encodes to the original bytes when `subprocess` hands it back as a pathspec); the comparison never decodes at all — it receives `str` pathspecs and only tests its own output bytes for emptiness. 🔴 **Both test that emptiness with `if p`, never `if p.strip()`**: `" "` is a legal filename, and stripping the RECORD drops it from the changed set, which is again a differing path reported as "identical" — MEASURED on git 2.55, a branch changing `a.md` (which lands) plus `" "` (which does not) gave `1 dead, 1 row would be removed`, with the evidence line `all 1 changed path(s) have identical content` on a branch that changed two. With `-z` the only empty record is the trailing terminator, so a bare truthiness test is correct and sufficient. Under the DEFAULT `core.quotePath=true` the old text-mode listing returned `café.md` as the literal `"caf\303\251.md"`; fed back as a pathspec it matched nothing and git exited **0 with empty output**, indistinguishable from "identical upstream", so `content-identical` fired and a worktree holding UNLANDED work was reported `dead` + `removable` (MEASURED on git 2.55: `verdict='dead' removable=True` before, `verdict='orphan' removable=False` after, with an ASCII-named twin correct at `orphan` on both — the twins pin that the fix did not break the ASCII answer, and that is ALL they pin). 🔴 **The twins are NOT the control against a fix that merely silences `content-identical` everywhere**, which an earlier wording of this row claimed and which `test_an_ascii_only_branch_is_still_classified_correctly`'s own docstring refutes: MEASURED, with `if not differ:` forced to `if False:` **both** twins PASS, because both their branches are unlanded and the signal is supposed to stay quiet on both. The control against a silencing fix is a fixture where the signal MUST fire — `test_content_identical_still_fires_for_a_landed_nonascii_path` and `test_squash_merged_branch_is_dead_not_orphan`. Do not trim those two on the strength of the twins. It needs EVERY genuinely-differing path in the set to be non-ASCII; one differing ASCII path answers correctly and saves the row. `PATHSPEC_BATCH_BYTES` now sizes each pathspec with `len(os.fsencode(p))` rather than `len(p)`, since a str undercounts a non-ASCII path by up to 4× and the budget is named in bytes. `--out` JSON gains `summary.submodule_blocked_dead` (dead rows the check holds back, `is not False` so **unanswered rows are in it**), `summary.submodule_unknown_dead` (the unanswered subset — NOT permanent, re-running may settle it), `summary.dead_not_removable` (the **union**, the one figure that is always true) and `summary.excluded_dead_only_blocker` (excluded dead rows whose *only* blocker is the exclusion). 🔴 `excluded_dead` and `submodule_blocked_dead` are counted **independently** and a row can be in both, so they do **not** necessarily sum — the report prints the measured overlap and the union rather than asserting either. 🔴 **A glob that matches nothing is byte-identical to no glob at all** — and `--confirm N` gives zero independent protection there, because N comes from the same wrong count — so the report ALWAYS echoes the effective glob list with a **per-glob** match count and names any glob matching zero rows. `--execute` refuses while a glob **you typed** is in that state; the built-in constant is never a refusal candidate (it cannot be mistyped, and refusing on it made the safety default block itself), and a scan that produced **zero rows** never refuses. **`--allow-unmatched-globs`** downgrades that refusal to a loud warning, for the correct-but-out-of-scope case a zero match cannot distinguish from a typo; it is echoed prominently in the report. Glob semantics: `fnmatch.fnmatchcase` against the absolute path; **`*` crosses `/`**; **subtree** (matching an ANCESTOR excludes the worktree, so naming a directory covers its contents); surrounding whitespace and a trailing `/` are stripped (in that order, by one shared normaliser); the symlink-resolved path is tested too, best-effort — a path whose ancestry contains a **symlink loop** contributes no resolved form rather than killing the scan (non-strict `Path.resolve()` raises `RuntimeError` on CPython 3.12.14 and does not on 3.13.15); the **first glob in the list** is the one credited, not the first path form that matches; a literal path containing `* ? [` needs `glob.escape` (note: `fnmatch` has no `escape`). The default glob is `*/.claude/worktrees/*`, **not** `…/agent-*` — 2 of 246 such entries on this box (2026-08-27; 1 the day before) have no `agent-` prefix and are live sessions' trees. 🔴 **`--out` JSON schema note**: `summary.exclude_globs` is a list of objects `{glob, typed, matched, matched_dead}` (it was a plain `list[str]` before this tool grew per-glob counts), and `summary` also carries `exclude_globs_blocking_execute`, `agent_worktrees_included`, `allow_unmatched_globs`, `agent_worktree_glob_in_force` and `agent_glob_applied_by_default`. `summarize()`'s `agent_worktrees_included` is **required and keyword-only** — it used to default to `False`, and a caller that opted the flag on in `resolve_exclude_globs` and omitted it here got `agent_worktree_glob_in_force=False` beside `agent_glob_applied_by_default=True`, a summary asserting the tool applies a constant that is not in the list. 🔴 **`agent_worktrees_included` is the FLAG; `agent_worktree_glob_in_force` is the FACT** — passing `--include-agent-worktrees` while re-typing `--exclude-path '*/.claude/worktrees/*'` sets the first and leaves the second True, and agent worktrees are still spared. The report's 🔴 opt-in warning is gated on the second, because gated on the first it printed a false alarm three lines above its own filter table saying the rows had been spared. 🔴 The zero-match refusal's *reassurance* — "that glob is applied by DEFAULT, dropping your hand-typed copy costs nothing" — is gated on a THIRD key, `agent_glob_applied_by_default` (= "is the tool applying the constant on its own?", computed once by the function of the same name and read, never re-derived, by every message about it): under `--include-agent-worktrees` the constant is **not** applied, so the hand-typed copy is the only thing sparing agent worktrees on that command line and "drop it" would advise the deleting-MORE direction. It is printed in **two** places (the stderr refusal and the text report) and both read that one key. 🔴 Two claims about the CURRENT run — the retyped-glob `note:` and the per-glob zero-match remedy — are conditional on **all three** of `--execute`'s refusal scopings, not on one of them: typed-globs-only, `--allow-unmatched-globs`, **and** *not when the scan produced no rows*. Each round of this PR closed one and left another open, on the stdout of a run that contradicted the sentence: round 5 printed "this run REFUSES" on a run that REMOVED, and round 6's fix still printed "--execute REFUSES while a typed glob is in this state" on a zero-row scan whose own stderr said "Not refusing." (rc 0). 🔴 And neither claim may assert removal **parity** with the default — round 6's "…it does NOT refuse and this run removes exactly what the default would have removed" is false the moment one more `--exclude-path` spares a row (measured: 0 removed against the bare default's 1, with the parity claim printed on that run). The flag decides refusal ELIGIBILITY; the glob list decides removals. A **bounded** claim is fine and the `note:` makes one — "this run can remove no more than the bare default would" is true because the run's glob list is a superset of the bare default's, so its removals are a subset; the banned shape is EQUALITY, not every mention of removals. (The earlier wording of this rule — "neither claim may say anything about *what is removed*" — forbade the note's own true sentence.) 🔴 Nor may either claim suggest that **dropping `--include-agent-worktrees` alone** could change the refusal: on the command line that prints the `note:` the constant is already in the glob list as a typed glob, so `resolve_exclude_globs`' `… and AGENT_WORKTREE_GLOB not in globs` conjunct is already False and the append it skips would have been a no-op. | script | purpose |

**rc 15 and the per-host allowlist.** `drift-check.sh` also reports HOST parity: **dangling managed symlinks** (rc 14) and **`settings.json` top-level key-name / `enabledPlugins` divergence** (rc 15). `settings.json` is per-host and unmanaged by design, so three keys — `theme`, `voice`, `effortLevel` — are **explicitly enumerated** as legitimately per-host, each with its reason in the source, and are reported as `IGNORED` rather than counted as drift. It is an enumeration and not a pattern **on purpose**: an unknown key is drift by default, the list is not env-overridable, and `permissions` is deliberately NOT on it (see `sync-claude-permissions.py`).

**rc 17 and rc 18 — SOURCE parity, the third kind.** Some `nix/pkgs/**` derivations build from a local working tree of ANOTHER repo (`${workspace}/…`), and nothing converges those: a host can be byte-identical to `origin/main` and still compile months-old code. rc 17 fires when a package's own `srcDir` **subtree** is behind/ahead its branch's own upstream (the repo-wide numbers are printed beside it as information only — scoping is what keeps this from being a permanently-red gate). rc 18 is its ladder: a scope that could not be evaluated at all is reported every run and escalates only after N **consecutive** runs, per (host, scope), reset the moment it measures — `no upstream` on the structural ladder (`DRIFT_UNMEASURED_ESCALATE`, default 4), a failed `fetch` on a longer one (`DRIFT_UNMEASURED_FETCH_ESCALATE`, default 12), and `repo ABSENT` on **neither**, at any count. Without it a scope stayed unmeasured forever while the run read as clean, which is the same "did not look" green rc 17 exists to refuse.

## Conventions

- Shell scripts use `#!/usr/bin/env bash`; Python uses `#!/usr/bin/env python3`.
- NixOS hosts: ad-hoc dependencies come via `nix-shell -p <pkg>`, never a system package manager.
- Indentation follows the repo-root `.editorconfig` (2-space default, 4 for Python).
- 🔴 Many of these are deployed by home-manager rather than run from this directory, so **a `git pull`
  changes nothing that nix manages.** An edit here takes effect only after
  `home-manager switch --flake ~/workspace/devrc --impure`. Whether a given deployed path is live or
  a store copy is answered by `readlink -f`, never by diffing it against this repo.
