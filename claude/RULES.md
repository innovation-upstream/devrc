# Claude Code Behavioral Rules

Priority legend: **🔴 CRITICAL** (security/data/prod — never compromise) · **🟡 IMPORTANT** (quality/maintainability — strong preference) · **🟢 RECOMMENDED** (apply when practical). On conflict: safety > scope > quality > speed; prototype vs prod differ.

🔴 **Read every rule at its WIDEST reading.** A rule names the case that bit us; the example is illustration, **not the boundary of the hazard** — if your case differs only in *why* you are doing the thing, the rule still applies. That is how a rule gets obeyed straight into the failure it forbids: the `git stash` ban read "never … to clear a tree for a rebase", so a subagent stashing to measure a *test baseline* proceeded and reached for a teammate's entry. When a rule looks inapplicable on a technicality, widen it and flag the wording — don't proceed.

📁 **This is the CORE: every rule that binds you is here, at full scope.** The worked incidents behind them — dates, byte counts, store paths, diagnoses, retracted theories — live in `claude/RULES-ARCHIVE.md`, NOT auto-loaded and NOT shipped to opencode; a `→ archive: <anchor>` tag means "evidence lives there". Read it for the *why*, or to check what was already tried — **never** to decide whether a rule applies. Nothing load-bearing is only there.

## Verification Honesty 🔴
**Triggers**: claiming "fixed/works/verified/done"; before commit/deploy

- **Reproduce the original symptom.** Never say verified/works/fixed unless you exercised the EXACT failing path and confirmed the symptom is gone. "Build passed", "pod is healthy", "deployed", "the adjacent code is correct" are prerequisites, NOT verification — and so are **a full green suite AND a clean adversarial audit**. → archive: green-and-audited-but-broken
- **Deployed ≠ verified.** State them separately. "Deployed 0.3.6; not yet verified against the click path" is honest; "shipped and verified" when you only confirmed the rollout is not. → archive: honest-phrasings
- 🔴 **A deploy reporting success is a claim about the DEPLOY, not about the CONSUMER.** After any deploy confirm the unit is `active` (not `activating`/`auto-restart`) **and** that the process holding the port is the one the unit started — an orphan can hold the port and serve OLD code while the converge check reports success. `ss -lptn 'sport = :<port>'` → listening PID; `/proc/<pid>/cgroup` (a real unit process reads `…/<unit>.service`); `systemctl --user show <unit> -p MainPID -p SubState` must agree. Kill an orphan by **resolved PID** — never let a `-f` pattern reach `pkill`. → archive: deploy-vs-consumer
- 🔴 **A live probe against a DIRTY tree is evidence about the DEPLOYED ARTIFACT, never about the committed source** — and must not overrule a red test. `git status` first; if dirty, say "verified the deployed copy, not `main`" — a feature can be **dead on `main`** and still probe green off an uncommitted fix baked into the deployed copy. Wherever a deploy step copies from a working tree (nix `home.file`, `rsync`, `docker build .`), "it works here" and "it is in the commit" are independent claims — **make both**. 🔴 **Same error in the TIME axis: current source is evidence about CURRENT behaviour, never what the code did BEFORE a fix** — and a file the fix CREATED is the worst witness to the bug. `git log --diff-filter=A -- <path>`, then `git show <fix-sha>^:<path>`. → archive: dirty-tree-probe
- **An audit/review fix RESETS the verification gate.** A change made in response to a review is a code change like any other — re-verify it live, never ship it on the reviewer's authority. An audit can be right about the gap while the fix is wrong about reality — one such fix shipped a **completely inert** feature. **Budget for SEVERAL rounds and re-audit the DELTA each time**: every delta audit found something the previous round's fix had introduced. → archive: audit-fix-resets-gate
- **When you can't verify, say so plainly** and hand the check to the user with exact steps.
- **For UI/interaction bugs, reproduce the user's actual click path** (Playwright) before claiming fixed — don't infer from the code.
- **One measurement is not a general claim.** When behavior depends on a dimension — depth, host, revision, cwd, timing, size, permissions — measure at ≥2 points (a boundary *and* a middle); behavior can differ, and even invert, between them. **Name the points you measured** so the claim carries its own scope. Applies double in a test assertion. In a comment state the claim; the measurement goes in the commit.
- **A field that exists in a DTO is not a guard — only a BRANCH on it is.** `git grep` the field name across consumers before assuming the case is handled. One payload's `notOwned` was declared in the consumer's own type and never read, so the not-owned case rendered a full zeroed dashboard as measured data — and "just set the field correctly" would have changed nothing on screen. **A type declaration is not a code path.**
- **Two changes touching one file: TEST-MERGE them, don't reason about it** (mechanics under Git Workflow). 🔴 But a **clean git merge is not a clean merge** — a *semantic* conflict survives it (both sides edit different lines of one function/config, result incoherent), so green means "no textual conflict", never "safe". Read the merged result of any overlapping region.

### 🔴 A test you have not watched FAIL proves nothing
- **A regression test must be shown to fail on pre-change code.** Report the matrix — "red at `<base-ref>`, green at HEAD". A guard pinning an invariant the bug never violated is an **invariant guard**: label it as one, don't count it as regression coverage. → archive: vacuous-guards
- 🔴 **Mutation-test a guard before certifying it — and prove it REACHABLE, not just breakable.** Break the thing on purpose and watch the guard go red; "I broke it and a test failed" is necessary, NOT sufficient, because a mutation test still passes when an earlier check always wins so the guard never executes, when a DIFFERENT guard's error kills your test (green for the wrong reason; still green with your guard deleted), or when the happy path resolves anyway. So: break it, **confirm a test fails with THIS guard's specific error/exit code**, then reach it with a case no earlier check rejects. → archive: unreachable-guards **A green sweep is only a claim about the mutations you IMAGINED.** Vary how the sweep is built, not just the mutant count; pick fixtures whose fields are pairwise distinct — **and distinct from any CONSTANT the assertion names**: a fixture that can only ever produce the constant's own value cannot see a mutant that hardcodes the literal, so it SURVIVES a fully green suite. The control is mechanical — feed a value the constant CANNOT equal and watch the output move. 🔴 **ISOLATE THE MUTATION: a mutant that removes a guard TOGETHER WITH ITS ENCLOSING CONDITION proves nothing about the guard, and dies for the wrong reason.** The shape: fixture constants that make the guarded branch land exactly ON its own boundary, so the guard never runs and its own assertion is unreachable while production's values would execute it. **Pick fixture bounds that overshoot, never a power-of-two multiple of the step**, and mutate the narrowest expression that can be wrong. **Re-verify an auditor's or subagent's self-reported mutation results** — exactly the claim asserted without being run. 🔴 And **validate the battery's own harness**: `grep -q "A|B"` matches `|` literally (BRE), and a `-run` filter that excludes the killing test reports SURVIVED — both produce confident, wrong coverage claims. → archive: mutation-sweep-blind-spots
- 🔴 **A SURVIVED mutant asserts the mutant RAN — and a stale bytecode cache means it usually did not.** CPython validates a cached module on source **mtime-in-whole-SECONDS + size**, so a **same-LENGTH** edit landing in the same second as the last import is invisible: the test imports the ORIGINAL bytecode and the mutant is scored SURVIVED without ever executing. `cp -a` (it preserves mtime *and* `__pycache__`) is a second route, **not a prerequisite** — an ordinary fast edit suffices, so "I copied nothing" is no defence. Widest reading: **any cache keyed on a coarse mtime**, not just `.pyc`. Sweep under `PYTHONDONTWRITEBYTECODE=1` (or delete `__pycache__` between mutants), and keep one mutant you KNOW is caught in the batch as the positive control. → archive: mutation-sweep-blind-spots
- 🔴 **"Verified in isolation" is the new vacuous green — the defect lives in the SEAM nobody owns.** Two components each hermetically tested, mutation-swept and audit-clean can still be broken TOGETHER: every test was scoped to one surface, so none ever built the combined state. **Ask which surface your fixture does NOT load.** A seam guard must pin a RELATIONSHIP, not a component — an asserted ledger of every writer/caller, failing when the set GROWS *or* SHRINKS — plus a behavioural case, since a structural check type-checks past a wrong argument. → archive: isolation-seam
- 🔴 **A guard can be SPELLED rather than STRUCTURAL** — ask: **can it pass while the hazard exists in a different shape?** Assert the STATE — id plus attribute, a role, an enumerated set — never a word another feature can spell. 🔴 **When the artifact under test IS prose, the mirror image: a guard on WORDS is walkable by REWORDING — pin the WHOLE normalised string.** Three walked in one PR. A cosmetic reword then fails the test — pay it, for a machine-readable claim. → archive: spelled-guards
- 🔴 **A guard's DESCRIPTION claims COVERAGE — check the implementation is as wide as the sentence.** The tell: a docstring names a RELATIONSHIP; the body inspects one SIDE. Six in one session, none a logic bug. Ask what the code must do to satisfy it, then check it does. **Reading as coverage while providing none is worse than none — it stops anyone looking.** → archive: guards-narrower
- **Never derive a test's expectation from the implementation it tests.** Stubbing a function to a no-op left 31 integration tests green. Pin literal expected values for contracts.
- **Write the claim AFTER the code, from what the function does.** A README asserted a privacy guarantee stronger than the code four rounds running, each round restating the intent instead of re-reading the implementation.

## Memory Is a Hypothesis, Not Ground Truth 🔴
**Triggers**: acting on a remembered fact — MEMORY.md, CLAUDE.md notes, prior diagnosis

- **Re-verify before acting on a remembered fact**, especially diagnoses ("X is caused by Y"), behavioral claims, and infra state. Memory reflects what was true when written.
- 🔴 **"Remembered" includes what YOU observed earlier in this same session — re-verify at the moment you ACT, not when you formed the plan.** A fact measured an hour ago is still a hypothesis about *now*, and it is invisible because the note in your head reads as first-hand knowledge. **The check belongs immediately before the destructive step, not in the survey that motivated it** — re-`stat`, re-read the row, re-run the query, and make the action conditional on what comes back. **Treat a clean outcome as luck, not as confirmation the check was unnecessary.** → archive: stale-observation
- **A memory that contradicts live reality is wrong** — surface it, correct it, update/delete it rather than acting on it.
- **Don't defend a stored claim against contradicting evidence** — the user correcting you is stronger signal than your note.

## Deterministic Over Prose; Push Back Before Acting 🟡
**Triggers**: fixing behavior, agent outputs, classification, form/field logic; any disagreement or risk

- **Prefer deterministic/structural fixes** over prompt-tuning, prose instructions, or suffix/keyword heuristics. If you reach for a prose/heuristic patch, say so explicitly and offer the deterministic alternative — let the user choose.
- **Flag BEFORE acting, not after.** Surface disagreement, risk, or a simpler path as a gate before the work: own your uncertainty, state the concrete blast radius, end with "your call to proceed." Stop before high-blast-radius autonomous actions (mass rollouts, prod changes) and get direction.
- **Don't defend your own position against repeated failure reports** — re-check instead; the user hitting the failure again outweighs your prior conclusion.
- **User-facing micro-decisions** (input controls, copy, button semantics, resource layout) with several reasonable options: present the choice briefly before building, don't ship-then-rework.
- **One rule, one place.** A predicate duplicated across call sites regenerates the same bug at every site — one such was re-fixed five times and only held once consolidated. When you find yourself patching the second copy, stop and consolidate. 🔴 **Consolidation is also a BUG-FINDING instrument, not just hygiene** — a predicate open-coded at N sites is typically wrong at N−1 of them *in the same direction*, and unifying them is what makes the disagreement audible. → archive: consolidation-finds-bugs

## Failure Investigation 🔴
**Triggers**: errors, test failures, unexpected behavior, tool failures

- **Root cause, not symptom**: investigate WHY a failure occurs and fix the underlying issue, don't work around it.
- 🔴 **An EMPTY RESULT cannot distinguish two mechanisms — go find the step that differs.** "Nothing happened" is the observable that the most causes share, so it identifies none of them, and picking whichever you already suspected is a coin flip you will record as a diagnosis. Before concluding from an absence, name the rival mechanism explicitly and ask which *upstream* signal — a request log, a counter, a span — the two disagree about. If no signal disagrees, you have not diagnosed anything; say so. → archive: empty-result
- **Never skip tests/validation** to make things pass — no disabling, commenting out, or bypassing checks.
- **Debug systematically**: read the error, investigate the tool failure, before switching approaches.
- **Run the cheap discriminating control BEFORE the plausible theory.** When a coherent environmental explanation is available (load, flake, a known historical bug), the *control* — an unmodified baseline, a pristine checkout, a second observation — costs less than the reasoning you'd do instead and is the only thing distinguishing "my change broke it" from "the environment is broken". A theory that explains the failure is not evidence for it. Corollary: **an absence of successes is not evidence of a defect** — check whether the path was ever exercised before diagnosing why it fails.

## A Green Test Suite Is a Claim, Not Evidence 🔴
**Triggers**: "tests pass", "CI is green", merging a batch of PRs, trusting a gate, reading ANY tool's verdict (harness, runner, scanner, grep)

- 🔴 **A green run covers only the tree and the environment it ran in — name what that combination structurally CANNOT see.** (a) **Gate on the MERGED tree, not the PR branch**: a PR green on its own branch and individually review-clean proves NOTHING about the tree its merge creates, because B's reviewer ran before A existed. **Build an integration branch off current main, merge every candidate, run the FULL suite there, and bisect the merge commits to attribute a failure**; also check how far behind main a PR is. → archive: merged-tree (b) **A suite that runs in TWO TIERS must be green in BOTH**: each tier's environment silently decides which tests execute, so a failure in one can be structurally INVISIBLE in the other. **Read BOTH tiers' output before believing either** — greening one tier while the other stays unobservable moves the bug, it does not remove it. → archive: two-tiers
- 🔴 **Validate the INSTRUMENT before you read its verdict — a tool's self-report is a claim about the TOOL, not about your code.** Applies to every harness, runner, wrapper, scanner and grep you take an answer from: until BOTH controls below have been watched to work, its result is a fact about the instrument only. **Negative control — can it go red?** Feed it a case it MUST fail; if that reports success it is testing nothing. Build the bad case from **REALISTIC data, not a textbook fixture** — scanners allowlist their own canonical examples and scan clean. → archive: nine-broken-harnesses **Positive control — can it ever observe the thing?** Going red does not prove it can, so a reassuring **zero** ("0 submits", "0 violations", "no matches") is indistinguishable from a harness wired to nothing: feed it a case that MUST produce a non-zero count, watch the number move, and **report the pair** — "1 on the positive control, 0 under test" — never the zero alone. → archive: positive-control **Read the CONTENT, never an exit code — COUNT.** A wrapper's trailing command swallows the status. Count `=== RUN` / `--- PASS` / `--- FAIL` / `--- SKIP` and grep for the timeout panic; **a known-red slow test must be `-skip`ped BY NAME**, or it eats the suite budget and silently truncates everything after it. → archive: count-not-exit-code **PARSING output makes its FORMAT a dependency you did not pin — "no matches" means "possibly the wrong pattern", not "nothing there".** Cross-check against a second tool that fails differently (`cmp` vs `diff`, exit status vs parsed summary); an empty match set is the zero above — unproven until a positive control shows the pattern CAN match. A **CLASS, not one manifestation**: the rule was read in-session and the trap was hit anyway, in new shapes. → archive: parsing-tool-output
- 🔴 **A count of DECLARATIONS is not a count of INSTANCES.** Grepping for a gate, guard, decorator or annotation counts the *sites*; the number that matters is what they *cover*. Measure that before quoting it — the site count looks like a nit while the instance count is the actual stake. → archive: declarations-vs-instances
- 🔴 **A test that skips itself, or passes by accident of the environment, is worse than no test — and a suite whose CONFIG pins a dimension is STRUCTURALLY BLIND to that dimension's bugs.** Every defect on the pinned dimension then passes vacuously, and new specs written into that config pass whether or not the fix works. Set viewport/locale/timezone/device explicitly, ask which dimension your config FIXES, and treat widening the harness as part of the fix, not extra work. → archive: config-blind-suite
- 🔴 **Distinguish a real failure from a load flake by WALL TIME (~15×), not by one re-run — and by WHOSE time moved: load inflates EVERY test in the run, a failed assertion inflates exactly ONE.** Read the other tests' times in the same run before calling it load; a single failed assertion decomposes as baseline + one `expect` timeout + teardown. A flaky test is also fixable — remove the timing dependency rather than re-running. → archive: flake-vs-assertion
- 🔴 **A permanently-red gate is worse than no gate** — it trains everyone to click through. Unbreak it or stop gating on it; never merge through a gate you have already called meaningless.
- 🔴 **A comment is a claim too.** Audit rounds repeatedly find comments the implementation contradicts — including a safety comment whose falsity would have led a maintainer to delete the guard it described. Tests assert what you believed; only reading the code against the comment tells you it still holds. When you close a hazard, update the comment describing it as open.

## Git Workflow 🔴
**Triggers**: session start, before changes, risky operations

These rules live HERE (managed, shipped to every host), not in `~/.claude/CLAUDE.md` — that file is per-host/mutable and does NOT ship, so a 🔴 rule placed there silently protects only one machine. `~/.claude/CLAUDE.md` is for genuinely host-specific facts (paths, OS, package manager) only.

- **Orientation: the harness already prints branch + status at session start — don't re-emit it.** No opening `git status && git branch`. When you genuinely need fresh state mid-session, one compact `git status -s && git log --oneline -3`. Orientation is not the safety check anyway — the next rule is, and it runs before every write, not once at the start.
- 🔴 **Re-check WHICH branch you are on before ANY write in a shared checkout — `commit` included, not just `pull`/`rebase`/`checkout`.** The switcher is **another session OR your own subagent**: a docs-only or read-only agent is exactly the case where `isolation: "worktree"` gets skipped, so its `git checkout -b <branch>` lands in *your* tree. **A `commit` onto the wrong branch is the silent one** — no conflict, no error, and `git log` afterwards shows exactly what you expect, because you are reading the branch you landed on. **`git branch --show-current` immediately before a commit** removes the whole class; **`git reflog`** is the one-command diagnosis when a branch looks like it moved backwards. → archive: wrong-branch-writes
- **`gh pr view <n> --json mergeable,mergeStateStatus` is the ONLY authority on whether a PR conflicts.** Don't infer it from a local merge trial: `git merge-tree <a> <b>` (git ≥2.38, two-arg `--write-tree`) prints only a **tree OID** on success — it emits NO `<<<<<<<` markers, so grepping for them finds nothing whether or not a conflict exists and reads as a confident "no conflicts" that is wrong. If you use it locally, **branch on the EXIT CODE** (non-zero = conflict), never on a marker grep. 🔴 **Same shape, different command: `git diff --quiet <ref> -- <path>` exits 0 when the path exists on NEITHER side** — used as a freshness check it returns a reassuring "matches `<ref>`" for a file that has never existed in that tree. Prove existence first (`git cat-file -e <ref>:<path>`, or `git log <ref> -- <path>`). Generalise: **a comparison against an absent operand reports SAME, not MISSING.**
- **Never `git add -A` / `--all` / `.`** — stage explicit paths. Blind-staging leaks unrelated WIP and secrets from a dirty tree. Enforced by the `bash-guard.py` PreToolUse hook.
- **Never `git reset --hard`** — it irreversibly destroys uncommitted work. Use `git restore <path>` / `git checkout -- <path>` for specific files, or `git checkout <ref> -- <paths>` to take another ref's version.
- 🔴 **Never `gh pr merge --delete-branch` a STACKED parent.** GitHub auto-closes any PR whose base branch is deleted and then **refuses to reopen it** — the branch is restorable, the PR object is not, so the child's review thread is lost. Merge a stacked parent **without** `--delete-branch`, or retarget the child first (`gh pr edit <child> --base <main-branch>`), then delete.
- 🔴 **A SQUASH merge NEVER makes the branch head an ancestor of the base** — so `git merge-base --is-ancestor <head> origin/main` returns **false after every squash merge**, forever. The squash is a NEW commit with different parents; the branch's own commits genuinely are not in `main`'s history. The false reads as "not merged — don't delete the branch / re-do the work", and it is wrong. **Verify a squash landed by CONTENT, never by ancestry:** the change is present in `origin/main` (diff the files) *and* the squash commit exists (`gh pr view <n> --json mergedAt,mergeCommit`).
- **Review before commit** (`git diff`); descriptive messages (avoid bare "fix"/"update"/"changes").
- **Commit/push only when asked.**
- **Feature branches only — never work on main/master; commit before risky operations for rollback.** The one exception: **repos whose own `CLAUDE.md` states that committing to the main branch IS deploying — currently only `homelab-talos`** (GitOps-reconciled from `trunk`). That written statement in the target repo is what makes the exception apply; you may not self-declare it, and it is not licence to commit to `main` anywhere else.
- 🟡 **Docs/notes written into a working tree are UNSAVED WORK** — a lesson, post-mortem, gotcha or script improvement in a tracked file is one routine `stash`/`checkout`/deploy by another session away from silent, unreported deletion. **Commit it or open a PR in the SAME session.** **Before dropping ANY stash, diff it against `HEAD`** — they have held work nobody knew existed. → archive: stranded-docs

### 🔴 `git stash` is repo-GLOBAL — never `git stash` in a shared repo, for ANY reason
🔴 **The prohibition is NOT scoped to rebases, and applies for ANY reason** — a narrower earlier wording is exactly how it failed (the preamble's example): knowing the rule did not help, because "hazardous for rebases" is not "don't". → archive: stash-incidents

**So: never `git stash` in any repo you share with other sessions, agents or humans.** `refs/stash` lives in the **common** git dir (`git rev-parse --git-common-dir`), not the per-worktree dir, so your own worktree gives you **zero** isolation and a concurrent agent or session can pop *your* stash. To set work aside, **copy it aside** (`cp <file> /tmp/…`, restore by copying back) or commit it to a throwaway branch. `git stash list` is a safe READ and will usually show pre-existing entries you must not disturb — if it is non-empty, that alone proves the stack is shared.

🔴 **When a file keeps reverting, find the WRITER before blaming the VCS operation you happened to be running.** A checksum guard wrapped around the suspected operation proves nothing if the real write happens elsewhere. → archive: sops-retraction (blaming stash/autostash for this is RETRACTED — do not re-derive it)

- **To sync a branch: use a clean worktree, not a stash.** The one recipe the rules below build on: `git -C <repo> worktree add ../<repo>-<topic> -b <branch> origin/<main-branch>` → edit/build/test/commit/push there → `git worktree remove`. A concurrent push then rebases only your clean tree.
- **To take another ref's version of a file:** `git checkout <ref> -- <paths>` — never stash/pop around it.
- **Worktree isolation is the standing default for any subagent that MODIFIES files** — pass `isolation: "worktree"`. Mandatory when agents run in parallel, or when another agent/session may share the repo: two file-modifying agents in one checkout **WILL** clobber each other. Read-only agents (audits/research/exploration) don't need one. Worktrees with no changes are auto-removed. If a worktree would drop needed uncommitted context, commit first or run a SINGLE agent in-place — **never** two file-modifying ones. **Forbid `git stash` in parallel-dispatch prompts.** 🔴 **But a worktree isolates a working DIRECTORY only. The surfaces it does NOT hand you — none of which a successful `worktree add` warns you about, and this list is not closed:**
  - 🔴 **the REPO it is built from is your CURRENT cwd's, not the one the task NAMES** — dispatch at a different repo and every agent gets a worktree of the wrong one. **For cross-repo work do NOT pass `isolation: "worktree"`** — have the agent run the recipe above with `-C <target-repo>` itself; that still satisfies the isolation mandate. **Two failure modes, only one loud:** the agent reports a briefed file missing (the tell), or it silently worktrees the right repo and proceeds, leaving your model of where the work happened wrong. → archive: cross-repo-worktree
  - 🔴 **the SESSION** — subagents share ONE scratchpad path and the branch namespace; a collision returns a confident GREEN computed against the wrong tree. Name every scratch dir per-agent, checksum the tree before/after a mutation battery, restore from `cp -a` not `git checkout --`, and detach a worktree that checked out a shared branch — it holds that branch repo-globally at whatever commit it stopped on. Usually your own fan-out, not "another session". → archive: worktree-not-session
  - 🔴 **the ENVIRONMENT** — `.envrc` is gitignored, so it never comes with the checkout: **wrong toolchain, none of the env the flake exports**, and agents reinvent workarounds the repo already solved. **`cp <repo>/.envrc <worktree>/ && direnv allow <worktree>`** at creation, dropping credential lines the task doesn't need (`use flake` alone suffices). Do both or neither — an `.envrc` never `direnv allow`ed errors on every `cd` into it. The tell: a toolchain binary "missing" in a worktree but present in the base clone. → archive: worktree-envrc
  - 🔴 **its SUBMODULES** — `worktree add` populates none of them, silently. The tell is a build/type error naming files your change never touched, in a module that EXISTS in the base clone — it reads as "the base branch is red" and gets reported as one. `git submodule update --init <path>`. → archive: worktree-submodules
  - 🔴 **any COPY you make OF it** — a worktree's `.git` is a FILE holding `gitdir: …`, not a directory, so a `cp -a` copy shares the ORIGINAL's git dir, index, refs and reflog: a `git commit` inside the copy lands on the REAL branch. The SESSION surface above tells you to make such copies. `rm -f <copy>/.git` immediately after any `cp -a` of a worktree. → archive: worktree-copy-git
- **Re-sync the base clone after worktree work merges** — worktrees do the committing, so the base clone is write-only and silently falls behind: `git -C <repo> fetch origin && git -C <repo> merge --ff-only origin/<main-branch>`. `--ff-only` is the point: it cannot conflict or autostash — it either fast-forwards or **refuses**, your signal the base clone diverged. If it refuses, prefer upstream; the base clone's side is almost always the stale one. **Dirty ≠ WIP — hash the working copy against that file's recent commits before treating it as WIP; byte-identical to an OLDER commit proves a stale orphan, and "restoring" it silently reverts everything since.** Recipe + the drift tells → archive: base-clone-drift

## Shell & Tooling Gotchas 🟡
**Triggers**: bash on NixOS/zsh hosts, Edit/Write, missing tools

- **zsh reserves `status`** — `status=$(...)` → `read-only variable: status`. Use `rc=`/`out=`.
- 🔴 **zsh's unbraced `$var` is NOT bash's — three traps, all returning a confident WRONG value with no error.** (a) **No word-splitting**: `for x in $SPACE_SEPARATED` loops **once** on the whole string, so a following `${x%%:*}` silently grabs the wrong field — use a literal list, a real array, or `${=var}`. (b) **History modifiers apply**: `$var` followed by `:` plus `e`/`h`/`t`/`r`/`s` is eaten as a modifier, so git refs (`$B:path`) and `host:/path` targets expand to a well-formed but WRONG string — **brace it: `${B}`**. (c) **Mirror image in a WRAPPER**: bare `$*` interpolated into an inner shell *does* split, turning a quoted `-g "some phrase"` into filename filters — zero tests run, reported as *"No tests found"* and **exit 0**; fix with `printf ' %q'`. Generalise: **a wrapper that reports "nothing to do" instead of erroring is how a green gets believed.** For any loop that mutates prod, add a per-item identity guard before the write. → archive: zsh-unbraced-var
- **`pgrep -f` / `pkill -f` match your OWN shell.** A wait loop like `while pgrep -f 'e2e/run.sh'; do …; done` never exits — the pattern appears in the loop's own command line. Worse, `pkill -f '<pattern>'` in a background script can **kill the script itself**. **Never let a `-f` pattern reach `pkill`** — resolve PIDs first: `pgrep -f <pat>` → skip `$$` → confirm each via `/proc/<pid>/cmdline` → `kill "$p"`. 🔴 **With parallel agents this widens: also confirm `/proc/<pid>/cwd` is your OWN worktree — the EXACT path, since agent worktrees nest under the base repo and a prefix matches every sibling. It does NOT separate two agents that BOTH sit in the base clone — read-only ones need no worktree, so that case is common and cwd cannot answer it.** A box-wide pattern reaches a *sibling agent's* processes: one auditor clearing its own hung run destroyed a sibling's test run, whose next attempt failed in a way that read exactly like a code defect in the branch under test. 🔴 **If no filter leaves a set you are confident in, kill nothing and hand it over.** → archive: sibling-agent-kill
- **NixOS: no apt/dnf** — for a missing tool (pandoc, pdftoppm/poppler, openpyxl, …) run it under `nix-shell -p <pkg> --run "..."` proactively; don't run bare, fail, then retry.
- **Is an edit to a home-manager-managed dotfile LIVE? `readlink -f` is the arbiter — never infer it from a `diff`.** **Terminates inside `~/workspace/devrc` → live** (an `mkOutOfStoreSymlink`; the working copy IS the live file, edits apply immediately); **terminates in `/nix/store` → needs a switch** (a `home.file` copy, so editing the repo does nothing). Byte-identical files prove nothing: identity can simply mean they are **one file**. → archive: readlink-arbiter
- **A `count=1` text replace on a pattern that occurs more than once is a live hazard.** Which occurrence you hit is not the one you pictured — grep the count first, and confirm by `git diff` which one moved *before* committing.
- **`grep` can render a character invisible.** A raw U+E000 in source printed identical to the untouched line, so an edit that had landed looked like it hadn't. When output "looks unchanged", inspect bytes — `sed -n l`, `xxd`, or `grep -P '\x{E000}'`.
- **`gh secret set` has NO `--body-file`** — omit `--body` entirely and it reads from **stdin** (`gh secret set NAME < file`). That is also the safe way: a secret in `--body` is exposed in argv/history.
- **GitHub sudo-mode re-auth cannot be automated** — creating a PAT (or any sudo-mode action) always stops at a passkey/TOTP/password gate. Hand that step to the user with exact instructions instead of burning turns trying to drive it.

## The Operator's Screen Is Not Yours To Take 🔴
**Triggers**: any command that raises a window, switches a workspace, or moves focus — `i3-msg`, `xdotool windowactivate`, `wmctrl`, `browser activate`

- 🔴 **Switching a workspace, raising or focusing a window changes what a human is looking at RIGHT NOW.** It is a `pkill`-class action, not a read. Never as a side effect of another task; never more than once per run; **never alternately** (ping-ponging between your window and theirs is the version that makes a machine unusable). → archive: screen-theft
- 🔴 **If a tool already performs the raise, do NOT run `i3-msg` by hand — that is a second theft, not a fix.** `browser activate` runs the host-side raise itself.
- **Record before you raise; restore before you finish, including on failure.** `PREV_WIN=$(xdotool getactivewindow)` and `PREV_WS=$(i3-msg -t get_workspaces | jq -r '.[]|select(.focused).num')` BEFORE the first raise — by the time you want them back the values are gone. Restore both at the end. If you cannot restore, say so in your report.
- 🔴 **A restore rule about FOCUS does not cover a WORKSPACE** — name both.
- **On a single-output host, "park on its own workspace" cannot mean zero switches** — every raise pulls the visible workspace. The achievable goal is *no ping-pong*: raise once, stay there for the run, restore at the end. Say which of the two you achieved; they are different claims.
- 🔴 **Prose alone has already failed to stop this twice** — a prohibitions list that omits the operator's screen reads as permission; absence next to present siblings is not neutral. → archive: screen-theft

## Files, Workspace & Safety 🟡
**Triggers**: file creation, library use, codebase changes

- **Place files by purpose**: reports/analyses → `claudedocs/`; tests → `tests/`/`__tests__/`; scripts → `scripts/`/`bin/`. Check for existing dirs/patterns first; never scatter `test_*`/`debug.sh` next to source.
- **Clean up**: remove temp files/artifacts before finishing; never leave anything that could be accidentally committed.
- **Respect the framework**: check deps (package.json etc.) before using a library; follow existing conventions and import style.

## Memory Hygiene 🟡
**Triggers**: writing to a project's auto-memory (`MEMORY.md` / `memory/` files); after finishing a piece of work

The auto-loaded `MEMORY.md` index costs tokens **every session** and has a hard byte cap (content past it is silently dropped on load). Topic files and skill bodies cost 0 until recalled/triggered — so the only per-session lever is keeping the index minimal.

- **Work-STATUS/progress does NOT belong in `MEMORY.md`** — shipped/verified/PR#/deployed/soaking state goes in a `claudedocs/` (or repo) handoff doc. An index entry is a durable *lesson*, not a status line; **prune it to `ARCHIVE.md` the moment the work ships.** Status re-bloat is the #1 cause of hitting the cap.
- **Domain ops-gotchas go in the matching skill** (`.claude/skills/<name>/SKILL.md`), not the index — the skill loads deterministically on trigger; re-loading it from the index is pure per-session cost.
- **`MEMORY.md` is only for cross-cutting lessons that map to NO skill** (git/shell/language/tooling tripwires).
- **Prune before you add**: if the index is near its cap, archive/dedupe first — don't just append.
- 🟡 **This file has the same economics, and a deterministic gate**: it loads EVERY session AND is concatenated into opencode's `AGENTS.md`, so it is paid twice. Its ceiling is enforced by `scripts/tests/test_rules_size.py`, which owns the constants and prints the eviction playbook on failure — **read the numbers there, never restate them.** Only the *imperative and its widest scope* belong here.
