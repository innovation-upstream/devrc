4. **Surface what past sessions already recorded — TWO recall surfaces, BOTH UNCONDITIONAL. Run both now, before the report:**

   ```bash
   $DEVRC/scripts/cairn-ops/read.sh recall --repo "<path>"
   python3 ~/workspace/devrc/scripts/lib/handoff_search.py --offline --query "<this handoff's topic, in plain words>" --limit 3 --exclude-slug "<the handoff: basename from step 2>"
   ```

   **Query the TOPIC, not an open item** — every resume has a topic; not every resume has an open item, and a step that can only run in the second case is a conditional. **What it is FOR:** the `Ruled out:` bullets scattered across the corpus are what stop you re-running a probe someone already ran, which is why the index is section-grained. When a specific open item is not covered by the topic query, run the command again with that item's own words.

   🔴 **`--exclude-slug` IS NOT OPTIONAL POLISH — WITHOUT IT THE TOP HIT IS THE DOC YOU JUST READ.** Measured over 20 real runs: the session's own handoff took **23 of 60** hit slots and was the **#1 hit in 13 of 20**. That is arithmetic, not a ranker bug — you are told to query the handoff's TOPIC, and the best text match for a doc's topic is that doc. Pass the value step 2 printed on its `handoff:` line; the flag also takes a bare slug or a `claudedocs/…` path. The freed slots go to documents you have **not** read.

   How to tell it landed: the run prints `excluded=<slug>` on its scope line and an `in_scope_docs` **lower than** `indexed_docs`. ⚠ Not necessarily by one — it excludes that slug in **every** repo. 🔴 `excluded=` proves the flag PARSED, not that it MATCHED — the count is the half that proves a match, so read the pair.

   🔴 **A zero from an excluded run: read the rc, not the prose.** Excluding every document the corpus could have answered with is `🔴 EMPTY SCOPE` at **rc 4** — your filter emptied it — and only a scope that still holds rows returns `NO MATCH` at rc 0. Both name the exclusion in their own output.

   🔴 **THE TWO SURFACES ARE NOT SCOPED ALIKE, AND THIS ONE IS CORPUS-WIDE.** `read.sh recall --repo` is scoped to one repo; `handoff_search` takes no `--repo` here and searches **every** repo in `handoff_index.REPO_ENV_HANDLES` — on this host `devrc`, `homelab-talos`, `datapacket-talos`, `civitai`, `$CIVITAI_CLI` — **three** of them client repos (`datapacket-talos`, `civitai`, and the CLI one). A devrc-topic query routinely returns client-repo sections above the devrc ones, and the tool's banner carries a staleness posture but **no** sensitivity language. So: read hits from another repo as recall, and **never paste one into a public repo or a client-facing artifact without checking which repo it came from** — the `<repo>/<slug>` on each hit is what tells you. Pass `--repo <label>` to scope it when that matters more than reach.

   ⚠ **`$CIVITAI_CLI` IS NAMED FOR ITS REMOTE, NOT FOR ITS DIRECTORY — THE BASENAME STILL DOES NOT MATCH THE HANDLE, SO GREP FOR THE HANDLE.** The handle is `CIVITAI_CLI`; the checkout it names is `~/workspace/civit/cli` and the repo LABEL the tool prints for it is therefore **`cli`** — that is what `--repo` takes. The durable consequence: `test_the_corpus_SCOPE_warning_names_the_repos_the_TOOL_actually_searches` matches **backticked tokens containing the handle name**, so naming `` `cli` `` in the SKILL.md body leaves it red — `cli` does not contain `civitai_cli`. The scope warning must spell `` `$CIVITAI_CLI` ``; the `--repo` flag must be given `cli`. Two different spellings for one repo, and nothing reconciles them for you.

   ⚠ **The label changed on 2026-10-02 and an older note here is why.** The handle used to resolve to `~/workspace/civit/civitai-cli` — a **second, dormant clone of the same remote** (`git@github.com:civitai/cli.git`) that is still on disk: 6 worktrees against the active clone's 71, working tree last moved 2026-06-18. That was invisible because `nix/agent-handles.nix` existence-guards every handle on `-d` and **both directories exist**, so the wrong one exported cleanly. It mattered because the indexer **never git-fetches** (the only `fetch` in `handoff_index.py` is `cur.fetchone()`, by design — `--offline` promises an answer from refs with no database), so the handle decides which clone's refs the corpus is read from and a dormant clone is a permanent, unbounded lag. Measured at the repoint: the dormant clone's `origin/main` carried **25** handoff docs against the active clone's **27**, and `indexed_docs` moved **560 → 562**. 🔴 The general lesson, which outlives this fix: **a handle guarded only on the directory existing cannot tell you it names the WRONG directory** — so when a repo's slice of the corpus looks thin, check which checkout the handle resolves to before concluding the docs are absent, and read an absence as "absent as of that clone's last fetch".

   🔴 **AND THE HANDLE LIST IS NOT THE REPO LIST — a repo outside it is INVISIBLE to both this tool and `find-session.py --arc`, which report that as a scoped zero rather than as missing coverage.** The four handles are four SPECIFIC checkouts, and a name that looks like a family is one directory: measured 2026-09-27, `$CIVITAI` is `/home/zach/workspace/civit/civitai`, so the sibling clone `civitai-app-starters` is in **no** handle. Two consequences, both of which read as answers: `find-session.py --arc <slug>` exits with *"no repo handle holds …"* having measured NOTHING, and `--exclude-slug` on a doc from such a repo **parses but cannot match** — the run prints `excluded=<slug>` while `in_scope_docs` stays EQUAL to `indexed_docs`, so the pair is the only thing that distinguishes "excluded one doc" from "excluded nothing, because that repo was never indexed". 🔴 **So read the pair, and before believing a zero about a repo, check the repo is actually a handle** (`echo $DEVRC $HOMELAB $DATAPACKET $CIVITAI`). Resolve an unhandled repo's arc by keyword instead: `find-session.py --all-time --all --json "<doc-slug>"`, which found all three sessions of one such arc. ⚠ Merging the doc to mainline does NOT fix this half — indexing needs the handle, not the branch.

   **Keep `--offline`** — it answers from git refs with **no database**; dropping it silently starts requiring one that no test has ever exercised. Every response carries a recall banner and the literal `indexed_docs=N indexed_sections=M`: a hit is a **POINTER TO VERIFY**, never a current reading, and it may describe a gotcha already fixed. 🔴 **A zero is not automatically an answer** — the tool names which zero it got and exits non-zero for the four that are not readings: **3** broken index (nothing was ever indexed) · **4** empty scope (your filter selected no rows) · **6** unmeasurable corpus (the repos did not resolve) · **7** the repos resolved and derived zero handoff docs. 🔴 **A fifth non-zero is not a zero at all** — rc **2**, usage: the `--exclude-slug` value named NO slug (blank, or a bare prefix/affix like `claudedocs`, `/`, `handoff-.md`), so the search never ran. It is reachable from THIS fence, because the value comes from step 2's `handoff:` line: fix the value and re-run, or drop the flag. Only `NO MATCH` at rc **0** means the corpus was asked and is silent. **Non-blocking:** on any non-zero, print the stderr line, say retrieval was unavailable, and carry on with the item.

   **The rest of this step is about `read.sh recall`, the first command.** It is `$DEVRC/scripts/cairn-ops/read.sh`, which refuses at rc **20** when no scope resolves. ⚠ Measured: the client refuses that shape too, at rc **2** naming the remedy — not with an empty report — so rc 20 is the same refusal in the wrapper's own ≥19 band, told apart from the store's.
